# 02 对抗验证报告 — EDA Agent System

> 全量对抗验证方法论 + 6 轮汇总。集训评审"验证了什么/发现什么/修了什么"一站式入口。
> 每个 finding 经对抗验证(读 CODE+测试核实,不盲信 agent major 判定)。

## 1. 对抗验证方法论

**fan-out + verify 两阶段**(ultracode workflow 模式):
1. **fan-out review**:多 agent 并行,每维度(schema 强制结构化输出 FINDINGS)扫一个角度,产出 findings 列表(severity/title/location/claim/evidence/suggested_fix)
2. **对抗 verify**:每 finding 独立 agent,默认怀疑,读 CODE+测试+文档逐字核实,尝试 REFUTE;警惕"看似矛盾实则已有兜底/测试覆盖"

**裁决原则**:CODE > CONTRACTS > 组件文档(冲突时改文档对齐代码,不臆测)。

**警惕误报**(T56 教训):5 个 major 里 2 个误报(_skill_* "双键兜底"没注意 / exit64 没查 test_cli_exit_codes:122 覆盖)。对抗验证必须读完整上下文。

## 5. 对抗验证累计价值

**误报辨伪率**(对抗验证关键价值 — 防止"看似 major 实则有兜底"):
- T56:5 major → 2 误报(40%)
- ultracode:24 findings → 2 误报(8%)
- 累计:29 major-class findings → 4 误报(14%)

**真 bug 挖出统计**:
- Phase 3:diagnose 预算真值陷阱(0.0 falsy 回退 60s)
- Phase 4:CPlanner 状态机时序(budget.exhausted 死循环 + 独立验证双触发)
- Phase 5:baseline_only 强制 rule + best_iter `or` 短路(0 被当 falsy)
- 复审:self_heal 预算 0.0 falsy(同 diagnose 漏修)+ opensta Action args_invalid(rule 模式 STA 从未真跑通)

**关键意义**:T56 文档互查 22 处闭环后,ultracode 6 维复审**仍挖出 2 真 CODE bug** — 证明"单轮验证不够,多角度 fan-out + 对抗核实"是集训前零遗留的关键。

## 6. 关键学习

1. **对抗验证必须读 CODE+测试逐字核实**,不能盲信 agent major 判定 — T56 5 major 里 2 误报(_skill_* 双键兜底 / exit64 测试覆盖),ultracode 2 误报
2. **CODE > CONTRACTS > 组件文档**裁决原则:冲突时改文档对齐代码,不臆测
3. **警惕"看似矛盾实则已有兜底"**:`_build_metrics` 双键兜底 / `severity_of` 默认 error 兜底 / `test_cli_exit_codes` 覆盖 — 这些都让"看似 major"实际 not_a_bug
4. **多轮验证叠加**:T56(文档互查)+ ultracode(代码+测试+文档三向)互补,单一角度不够
5. **schema 强制结构化输出**(FINDINGS/VERDICT)让 agent 输出可机器核验,避免散漫
